# Plan: OpenVPN, community translations, macOS and Windows

Status: OpenVPN **done** (2026-10-29, `src/ovpn.rs`, see
`docs/ARCHITECTURE.md`; still to test on a real server); the rest is thinking
ahead. Order decided by the maintainer: OpenVPN, then the shared core, then Windows,
then macOS. Translations through Weblate once the repository is public.

## 1. OpenVPN profiles (done)

What was built follows this section, with three changes: certificates live in
`~/.cert/nm-openvpn/` (SELinux on Fedora), the password may also be typed in the
editor, and OpenConnect is left for later. Packages list the plugin as a
recommended dependency (`docs/plans/ci-and-release.md`).

### How

NetworkManager already runs OpenVPN through its plugin
(`network-manager-openvpn`, installed by default on Ubuntu and Fedora
desktops). Tunnelbird keeps its architecture: it writes a NetworkManager
profile of type `vpn` (`service-type = org.freedesktop.NetworkManager.openvpn`)
and activates it, exactly like WireGuard profiles today.

- **Import**: NetworkManager's own `.ovpn` importer lives in the plugin's C
  library, not on D-Bus. Tunnelbird parses `.ovpn` itself (new `src/ovpn.rs`,
  pure and unit-tested like `config.rs`) for the options providers actually
  use: `remote`, `proto`, `port`, `dev`, `cipher`/`data-ciphers`, `auth`,
  `auth-user-pass`, `tls-auth`/`tls-crypt`, `remote-cert-tls`, `verify-x509-name`,
  inline `<ca>`, `<cert>`, `<key>`, `<tls-auth>`, `<tls-crypt>`.
  Anything else is listed as “ignored settings”, like today.
- **Certificates**: the plugin wants file paths. Inline blocks are written to
  `$XDG_DATA_HOME/tunnelbird/openvpn/<uuid>/` (mode 0600, removed with the
  tunnel), the same idea as `nm-connection-editor`'s `~/.cert/nm-openvpn/`.
  In Flatpak and Snap this folder is the app's own, and NetworkManager (root)
  can read it.
- **Passwords** (`auth-user-pass`): the editor asks for the user name and
  stores the password through NetworkManager with “agent-owned” flags, so the
  desktop keyring keeps it. GNOME Shell already answers NetworkManager's
  password prompts; a Tunnelbird secret agent (D-Bus
  `org.freedesktop.NetworkManager.SecretAgent`) is only needed for desktops
  without one.
- **Plugin missing**: activation fails with a known error → a clear message
  with the install command (`sudo apt install network-manager-openvpn`).
- **What changes in the UI**: type “OpenVPN” instead of “WireGuard®”, the
  editor shows server, protocol and user name (advanced options stay
  read-only), QR sharing is WireGuard-only (no mobile standard for `.ovpn` in
  a QR code), export writes back the `.ovpn`.
- Traffic graph, location, one-tunnel-at-a-time, trusted networks and the top
  bar work unchanged (the interface is `tun0`-like). The “server not
  responding” check needs another signal than WireGuard's (OpenVPN pings
  through its control channel): use NetworkManager's state changes instead.

Effort: about a week (parser and tests, editor variant, secrets, docs).

**Decision**: OpenVPN only, or also the plugins NetworkManager has for
OpenConnect (Cisco AnyConnect, used by companies and universities)? The same
pattern covers both.

## 2. Community translations (Weblate)

- **Where**: Hosted Weblate gives free hosting to open-source projects
  (“Libre” plan: public repository, OSI license, GPL-3.0 qualifies). Request
  it once the repository is public.
- **What it needs from the repository**:
  1. `po/tunnelbird.pot` committed and regenerated by CI on each change to the
     sources (needs `xgettext` ≥ 0.24 for `--language=Rust`; older versions, such as
     0.23, lack it: CI uses a recent gettext, or `--language=C`, which reads
     Rust strings well enough for `gettext("…")` calls).
  2. Store texts translated through gettext too: `data/*.desktop.in` and
     `data/*.metainfo.xml.in`, merged at build time with `msgfmt --desktop` /
     `msgfmt --xml`, instead of the hand-written `[fr]` / `xml:lang="fr"`
     lines. Then a translator also translates the store listing and the
     screenshots captions.
  3. Languages from `po/LINGUAS` only: `build.rs` generates the list shown in
     Preferences (code + the language's own name from the `.po` header), so a
     new language needs no code change.
  4. CI checks every `.po` (`msgfmt --check`) and that `make screenshots` runs
     for each language (screenshots per language come for free).
- **Workflow**: Weblate commits to its own fork and opens pull requests;
  translators never need a GitHub account.
- Docs: `docs/TRANSLATING.md` points to Weblate first, `.po` files second.

Effort: a day or two.

## 3. macOS and Windows

The Linux app is Linux-only by design: GTK/libadwaita for the window and
NetworkManager for the tunnels. Other systems need another tunnel backend and,
to feel native, another interface. What can be shared is the logic.

**Where it stands**: the shared core and the service exist; the macOS app is
built and runs on Apple silicon, not released (step 3); Windows is written but
has never run (step 2).

### Step 1: a shared core (done, `crates/core`)

Move the pure parts into a `tunnelbird-core` crate (Cargo workspace):
`config.rs` (parser), `provider.rs`, `trust.rs` (decision only), `health.rs`,
the version logic of `update.rs`, the future `ovpn.rs`. No GTK, no D-Bus, all
unit-tested. The Linux app becomes one client of that core.

### Step 2: Windows (first: larger audience, simpler than macOS)

Started: the interface ↔ service protocol is defined and tested
(`crates/core/src/protocol.rs`, described in `docs/PROTOCOL.md`); the same one
serves macOS. The service exists (`crates/service`): request handling, one
tunnel at a time, storage and Unix socket, tested with a fake backend. Its
Windows part (WireGuardNT, ovpn-dco-win, named pipe, DPAPI, Windows service)
is written blind on Linux; it compiles for Windows but has never run. Its
macOS part (BoringTun, `openvpn`, launchd) has since run on a Mac. Hand-off
with first-run steps: `docs/WINDOWS.md`, `docs/MACOS.md`.

- **Tunnels**: WireGuardNT (kernel driver, `wireguard.dll`, signed by its
  authors) for WireGuard, and OpenVPN's `ovpn-dco-win` driver for OpenVPN.
  Creating adapters needs administrator rights, so the design is the classic
  one: a small Windows **service** (runs as SYSTEM, written in Rust) owns the
  tunnels; the interface runs as the user and talks to it over a named pipe.
- **Interface**: native **WinUI 3** (Windows App SDK, C#): Fluent style, Mica,
  icon in the notification area, like Windows 11's own apps. It only shows
  things and sends clicks: all the logic is in the Rust core and the service,
  over the named pipe (a small documented JSON protocol, the same as on
  macOS). Built with the free .NET SDK.
- **Distribution**: maintainer's decision, **no store**: an installer downloaded
  from the website (an `.msi` installing the app and the service), plus `winget`
  later if wanted. The drivers are already signed by their authors, so only
  Tunnelbird's own files would be unsigned: Windows SmartScreen then shows
  “Windows protected your PC” → “More info” → “Run anyway” on each new
  version, and antivirus false alarms are more likely. Free way out for
  open-source projects: the SignPath Foundation signs releases at no cost
  (application once the repository is public).
- Check licences before shipping: WireGuardNT and Wintun have their own terms
  for redistribution. The trademark rule stays: the type “WireGuard®” as a
  label, never the logo.

### Step 3: macOS

**Status**: the app and the service are done and run on a MacBook Air (Apple
silicon, macOS 27.2): WireGuard® and OpenVPN tunnels, IPv6 block, crash
recovery, install from the `.dmg`, “Open Anyway”. Not released. What is left:
CI building the `.dmg`, the website's macOS tab, Intel, and the cases
`docs/COMPATIBILITY.md` marks as not run (`docs/MACOS.md`, “Still to do”).

- **Distribution**: maintainer's decision, **no store and no paid Apple account**:
  a `.dmg` downloaded from the website.
- **Consequence for the tunnels**: Apple's VPN framework (NetworkExtension)
  needs an entitlement that only a paid developer account can grant, even
  outside the App Store. Without it, Tunnelbird works like `wg-quick` from
  Homebrew or Tunnelblick: a small **helper running as root** (launchd daemon,
  Rust, BoringTun for WireGuard and the `openvpn` program for OpenVPN) creates
  the `utun` interface, sets routes and DNS; the app talks to it over a local
  socket. The helper is installed once, with the administrator password.
- **Consequence for the first launch**: an unsigned app is blocked by
  Gatekeeper. Since macOS 15 the user opens System Settings › Privacy &
  Security › “Open Anyway” once per version (the website shows it with
  screenshots). If this proves too rough, a paid account can be added later
  without changing the design much.
- **Interface**: native **SwiftUI**, as a menu bar app (`MenuBarExtra`) with a
  main window, like most Mac VPN apps. It talks to the root helper over the
  local socket with the same protocol as Windows. Built with the free command
  line tools (`apple/build.sh`); Xcode is not needed.
- OpenVPN runs through the `openvpn` program started by the helper; WireGuard
  first.

### How the maintainer works on these systems

macOS is developed directly on a Mac, with the free command line tools. Windows
stays to do on a Windows PC. Never a self-hosted CI runner on these machines
once the repository is public: anyone's pull request could run code on them;
GitHub's hosted Mac and Windows runners (free for public repositories) build the
releases.

Effort: weeks for each system; no yearly cost with the choices above.

**Decided**: no store and no paid account (the project spends nothing),
installers from the website only; native interfaces (WinUI 3, SwiftUI) on top
of the shared Rust core; the maintainer has a Windows PC and a Mac to test once the
app works. Tauri + Svelte stays the fallback if the remote round trips become
a burden. The shared core exists (`crates/core`). **Still open**: apply to the SignPath
Foundation once public.

## Also worth considering later

- **IPv6 leak and kill switch**: optionally block traffic outside the tunnel
  while connected (NetworkManager can't do it alone: nftables rules through a
  small privileged helper, or the firewall zone). Asked by privacy-minded users.
- **Split tunnelling per app**: hard on Linux without root; probably never.
- **Several tunnels at once** (home + office split tunnels): the “one at a
  time” rule could allow two non-overlapping split tunnels.
